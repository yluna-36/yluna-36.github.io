[格物-005] 当 Codex 能复刻一个热门 App，独立开发者还剩什么壁垒？
yluna
  2026-11-23 13:35:00   2026-11-23 13:35:00  
  • 方法论
  4114 Words  7 Mins  

最近了解了两个项目，我的第一反应竟然出奇地一致：

这东西好像没什么技术难度，我用 Codex 也能写出来吧？

一个是开源应用商店 Komi Store，另一个是曾经爆火的「死了么」App。

但仔细研究之后，我发现，比起它们实现了什么功能，更值得思考的是：为什么这么简单的东西，偏偏能被别人做成热门产品？

一、两万 Star 的项目，可能只是给 GitHub 套了个界面？

Komi Store 是一个开源应用商店。它把 GitHub、Codeberg 等平台上开发者已经发布的软件集中起来，帮助用户搜索、下载、安装和管理应用。

截至 2026 年 11 月 23 日，它的 GitHub Star 数量已经达到约 2.2 万。

刚开始看到它时，我甚至有些困惑。

因为这个想法实在太容易理解了：GitHub 已经有项目搜索和 Releases，为什么不能再开发一个图形化界面，把这些功能包装成应用商店？

这不就是一个 API 集成项目吗？

更何况，类似的想法并不新鲜。早在 Komi Store 之前，Obtainium 就已经能帮助 Android 用户从 GitHub 等来源下载和更新应用。

如今借助 Codex，开发这样的产品，至少在核心功能层面，门槛比以前低了很多。

但随之而来的，是另一个问题。

Komi Store 的目标是帮助不懂 GitHub 的普通用户，可是愿意给它点 Star 的人，不恰恰是已经会使用 GitHub 的人吗？

这让我意识到一个经常被忽略的事实：

GitHub Star 并不等于真实用户，更不等于付费用户。

一个项目在开发者社区里很受欢迎，并不能直接证明它已经成功触达了目标用户。

当然，这并不意味着 Komi Store 没有价值。

会使用 GitHub，不代表愿意每次都手动寻找安装包；开发者也可能成为产品的传播者，把它推荐给不懂技术的朋友。

而且，把多个平台的版本识别、下载、更新、兼容性和安全校验做好，也远不只是写几个 API 请求那么简单。

但是，技术实现、用户增长和商业成功，显然是三个不同的问题。

能做出来，是工程问题；有人愿意用，是产品问题；有人愿意持续付费，则是商业问题。

二、「死了么」：一个容易复制，却不容易做成的产品

相比 Komi Store，「死了么」App 更让我感兴趣。

它最初的功能简单得令人惊讶：用户每天打开 App 签到。如果连续两天没有签到，系统就向预设的紧急联系人发送邮件。

没有复杂的算法，没有庞大的功能体系，也没有什么看得见的技术突破。

2026 年 1 月，这款 App 却迅速走红，一度登上苹果中国区付费应用榜榜首。

更有意思的是，据第一财经报道，有开发者借助 Gemini，仅用约六个小时就制作出了功能类似的「活着么」。

但如果实现如此容易，为什么最先爆火的偏偏是「死了么」？

一开始，我认为它最大的价值在于发现了一个难以察觉的需求。

后来查阅资料发现，事情更加有趣。

早在 2024 年 12 月，就已经有网友提出过独居者每天签到、避免发生意外却无人知晓的 App 创意。《中国青年报》对此有过报道。

也就是说，这个想法不是第一次出现，功能也不是第一次被实现。

那么它究竟做对了什么？

首先，它把一个模糊的生活焦虑，变成了可以理解的具体功能。

独居者真正担心的，也许不是忘记签到，而是：

如果某一天我突然发生意外，会不会根本没有人发现？

「死了么」将这种难以表达的担忧，转化为一个非常直接的产品。

其次，它选择了一个极具传播性的名字。

名字本身就能引发讨论。即使一个人完全不需要这个 App，也可能因为好奇而了解它。

这让产品获得了远超自身功能复杂度的传播效果。

但我们也应该区分：一次病毒式传播，不代表一个已经得到长期验证的需求。

每天签到能否坚持？忘记签到会不会造成误报？紧急联系人能否及时响应？这些问题都不是靠爆火就能自动解决的。

而它后来的发展恰好提供了另一种观察视角。

2026 年 1 月，这款产品曾宣布启用 Demumu 品牌；到了同年 5 月，它又更名为「在么在么」，逐步从年轻人的独居签到工具转向老年安全监护。

根据2026 年 10 月的报道，团队开始探索面向社区与政府的安全监护服务，并公布了每年 99 元和 199 元的方案。但当时有关付费功能仍处于推广阶段，不能把报价直接当成已经实现的收入。

最初吸引关注的是年轻人的独居焦虑，后来探索的场景却是老年安全监护。

产品找到的第一个需求，未必就是最终能支撑商业化的需求。

三、AI 正在降低开发门槛，但没有消除产品门槛

这两个案例让我重新思考独立开发的价值。

过去，一个人有了好的 App 创意，还需要考虑大量技术问题。

会不会编程？能不能独立开发前后端？有没有能力部署服务器？能否适配不同设备？

这些门槛足以让很多创意停留在想法阶段。

但现在，Codex 等 AI 编程工具正在快速降低其中一部分成本。

一个人就可以尝试完成过去需要多人协作的工作。

这意味着软件开发正在发生一种变化：

代码的供给越来越充足，真正值得解决的问题却没有因此自动增加。

当越来越多的人能够低成本开发软件，单纯的「我能把这个功能实现出来」，就不再是足够强的竞争优势。

这时候，另外几种能力反而可能变得更加重要：

  • 发现需求：不是凭空想象一个功能，而是发现人们反复遇到、尚未得到妥善解决的问题。
  • 验证需求：用户说「不错」，不等于用户每天会用；愿意试用，也不等于愿意付费。
  • 表达与传播：产品如何被迅速理解、记住和推荐，决定了它能否走出开发者自己的圈子。
  • 持续交付：安全性、可靠性、异常处理和长期维护，不会因为 AI 能写代码就自动完成。

AI 让产品的第一个版本变得便宜，却不会自动让一个产品值得信任。

四、那么，独立开发者应该怎么做？

如果现在让我从零开始做一个独立产品，我可能会调整思考顺序。

以前的思路是：

先想到一个有趣的功能，再考虑怎么实现。

现在我更倾向于：

先寻找真实存在的问题，再用 AI 低成本验证解决方案。

例如，观察社交平台上人们反复抱怨什么，看看现有软件的差评集中在哪里，或者研究某个群体为什么不得不用繁琐的手工流程完成一件事。

一个尤其值得关注的信号是：

如果用户已经在为某个问题付出时间、金钱或者精力，那么这个需求往往比一句「我觉得这个功能不错」更值得研究。

接下来，不必急着开发完整产品。

可以先用 Codex 制作一个最小可用版本，让真实用户尝试。

如果没人需要，就及时停止；如果有人反复使用，再逐渐完善功能、研究传播和商业化。

AI 编程真正带来的机会，也许不是让每个人都去开发更多 App，而是让我们能够以更低的成本，验证更多原本不值得投入大量资源的想法。

五、最后：想法容易，代码也越来越容易，那什么最难？

回到最初的两个项目。

Komi Store 的功能不算难以想象，类似方案早就有人做过。

「死了么」的功能更简单，不仅创意早就出现，走红后甚至有人用 AI 在几个小时内做出了类似产品。

如果只是讨论技术可复制性，它们都没有一道不可逾越的护城河。

但这不意味着任何人都能复制它们的成功。

复制功能，不等于复制需求；复制产品，不等于复制用户；复制流量，更不等于复制商业模式。

随着 AI 编程工具的发展，独立开发者的竞争，可能会越来越少地集中在「谁能把代码写出来」，而越来越多地集中在「谁能够找到真正值得解决的问题，并把解决方案送到需要它的人面前」。

这对独立开发者来说，既是挑战，也是机会。

毕竟，过去一个好想法可能因为技术能力不足而无法实现。

现在，至少我们可以先把它做出来，再看看世界是否真的需要它。

AI 正在让编程变得更容易，但理解人的需求，依然是一件困难的事。
